# 拖拽分析测试 Agent —— 设计方案

> 目的:让一个 Agent 像真实分析师一样,反复用「Flint 图表工作台」完成 Tableau 里有代表性的拖拽分析,
> 自动发现 **做不到的功能、算错的数、难用的交互**,输出可执行的改进清单,驱动产品一轮轮迭代。
> 本文只做设计,不含实现。

---

## 1. 总体思路:一个闭环

```
 ┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌─────────────┐   ┌───────────┐
 │ ① 场景库     │──▶│ ② 执行 Agent  │──▶│ ③ 判定(Oracle)│──▶│ ④ 问题分诊   │──▶│ ⑤ 修复/迭代 │
 │ Tableau 任务 │   │ 在浏览器里操作 │   │ 数对不对、图对不对│   │ Bug/体验/缺功能│   │ 改代码→回归 │
 └─────────────┘   └──────────────┘   │ 好不好用      │   └─────────────┘   └─────┬─────┘
        ▲                              └──────────────┘                          │
        └──────────────────────── 场景通过后进入回归集,新功能补新场景 ◀──────────────┘
```

关键设计决定:

1. **两种 Agent 分工**
   - **脚本 Agent(回归)**:用确定的操作步骤跑每个场景,快、稳定、零成本,每次改代码都跑。回答"功能坏没坏、数对不对"。
   - **探索 Agent(体验)**:一个 LLM Agent 只拿到自然语言任务(如"看各大区每季度利润,只看 2024 年,按利润排序"),
     自己看截图和页面结构去摸索怎么操作。回答"一个新用户能不能做出来、要绕几步、卡在哪"。**"好难用"这个问题只有它能量化。**
2. **判定不靠 Agent 自己说"成功了"**:每个场景都有一份独立计算的标准答案(用 SQLite/pandas 直接算原始 Excel),
   和工作台送给 Flint 的数据逐行比对。图形层面再做结构检查(标记数量、图例、坐标轴、溢出)。
3. **以 Tableau 为基准打分**:每个场景记录"Tableau 熟手需要几步",和 Agent 实际步数对比,得到**操作成本比**。

## 2. 场景库:把 Tableau 的拖拽分析拆成可测试的任务

每个场景是一个 YAML 文件,结构如下(示例):

```yaml
id: T03
title: 各大区每季度利润趋势
tableau_feature: 日期层级(年→季度)、颜色分系列
dataset: sales_fixture.xlsx          # 固定的测试数据,答案已知
goal: "看各大区每个季度的利润变化趋势"   # 探索 Agent 只看这一句
tableau_steps: 3                      # Tableau 熟手:订单日期→列,利润→行,大区→颜色;日期右键选季度
script:                               # 脚本 Agent 的确定步骤(用操作层 API,见 §4.2)
  - chartType: Line Chart
  - drag: {field: 订单日期, to: x, timeUnit: quarter}
  - drag: {field: 利润, to: y, agg: sum}
  - drag: {field: 大区, to: color}
expect:
  sql: |
    SELECT strftime('%Y',"订单日期")||'-Q'||((CAST(strftime('%m',"订单日期") AS INT)+2)/3) AS q,
           "大区", SUM("利润") AS v FROM data GROUP BY 1,2
  chart: {marks: line, series: 6, x_ticks_min: 8}
priority: P0
```

## 3. 测试数据(Fixtures)

- **sales_fixture.xlsx**:在现有造数基础上**加入可控的"坑"**,答案全部已知:
  - 一个大区全年利润为负(测 C04、负值轴);一个月份没有数据(测断档);
  - 一个类别名带空格和逗号、一个带英文引号(测解析与筛选);若干空值(测 null 处理);
  - 客户 ID 列(测 COUNTD、LOD);目标销售额列(测子弹图、参考线);
  - 跨 3 年,含闰年 2 月 29 日(测日期粒度和星期)。
- **multi_sheet.xlsx**:订单表 + 退货表(测 H03)。
- **wide_table.xlsx**:宽表,每月一列(测"宽转长",Tableau 的数据透视)。
- **big.xlsx**:15 万行(测性能)。

每个 fixture 配一个 `answers.sqlite`,Oracle 直接在里面跑场景的 `expect.sql`。

## 4. 执行 Agent

### 4.1 运行环境

| 环境 | 用途 | 说明 |
|---|---|---|
| 本地/CI 构建(`npm start` 起在 localhost) | 主力:每次改代码都跑 | 数据隔离、可重置、可并行 |
| 线上 `http://152.136.222.86:39018` | 只做每日冒烟(5 个 P0 场景) | 用 `__agent_test_` 前缀的数据集,跑完删除。**注意:云端 Claude 会话的网络默认访问不到这个地址**,冒烟要在你本机或 GitHub Actions 里跑,或在环境网络设置里放行这个 IP |

### 4.2 产品侧要先补的"可测试性"(第 0 阶段,约 1 天)

1. **稳定选择器**:所有可操作元素加 `data-testid`(字段 `field-<名称>`、通道 `slot-x`、聚合 `agg-x`、图表类型、筛选器……)。
2. **调试钩子**:`window.__studio = { getSpec(), getTable(), getConfig(), getValidation() }`,让 Oracle 拿到送给 Flint 的数据。
3. **重置接口**:`POST /api/__reset`(仅在 `TEST_MODE=1` 时开放),清空数据集和图表。
4. **操作层 API**(脚本 Agent 用,写在测试代码里):`upload(file)`、`setChartType(t)`、`drag(field, channel)`(真实 HTML5 拖拽,不是直接改下拉)、
   `setAgg(channel, agg)`、`setTimeUnit(channel, unit)`、`addFilter(...)`、`sort(...)`、`topN(n)`、`setProp(key, v)`、`save()`、`reload()`。

### 4.3 脚本 Agent(回归)

- Playwright 跑场景 YAML 的 `script`,每步后截图;步骤里的操作全部走真实 UI(拖拽用 `dragTo`),不调内部函数。
- 场景标为 ❌ 时期望它失败,并记录"失败在哪一步",作为缺口证据;功能补上后状态自动翻转。

### 4.4 探索 Agent(体验)

- **输入**:场景 `goal` 一句话 + 数据集;**不给**操作步骤和选择器。
- **能力**:截图 + 可访问性树(Playwright MCP 的 `browser_snapshot`),动作只有点击、拖拽、输入、选择、滚动——和真人一样。
- **约束**:最多 25 步;每步必须写一句"我在找什么 / 我以为会发生什么"(这就是用户心智的记录)。
- **结束**:Agent 声明完成后,由 Oracle 判定,Agent 自己说了不算。
- **人设轮换**:同一场景用三种人设各跑一次——Tableau 老用户(会找"行/列"架子、右键菜单、双击)、Excel 用户(找"数据透视表")、新手(只看界面文字)。
- **记录的体验指标**:

| 指标 | 含义 |
|---|---|
| 成功率 | Oracle 判定通过的比例 |
| 操作成本比 | Agent 步数 ÷ Tableau 熟手步数(目标 ≤ 1.5) |
| 走错路次数 | 点了又撤回、打开又关闭的次数 |
| 卡点 | 连续 3 步没进展的位置 + Agent 当时的想法 |
| 期望落空 | Agent 写"我以为…"但实际没发生的地方(最有价值的改进线索) |

## 5. 判定(Oracle)

每个场景跑完按四层判定,任一层不过就记问题:

1. **数据正确性(最重要)**:`__studio.getTable()` 与 `expect.sql` 的结果比对——行数一致、维度值集合一致、度量值误差 ≤ 0.01%、排序符合要求。
2. **规格合规**:Flint `validateChart` 无 error;语义类型合理(金额是 Amount、日期粒度对应 YearMonth/YearQuarter 等);通道映射符合场景要求。
3. **渲染结构**:SVG 存在;标记数量与数据行数相符;系列数、图例项、坐标轴刻度满足 `expect.chart`;图表不溢出容器、标签不重叠(包围盒检测);控制台零报错。
4. **视觉评审(抽样)**:把截图交给一个评审模型,按固定量表打分(是否一眼能读出结论、标题是否说明问题、颜色是否区分得开、是否有截断)。只作为参考,不作为通过条件。

另加两项全局检查:首屏加载 < 3 秒、配置改动到出图 < 500ms(15 万行数据 < 2 秒)。

## 6. 问题分诊与输出

每轮跑完生成一份报告(Markdown + 截图,可发布为网页),包含:

- **覆盖矩阵**:55 个场景 × (脚本通过 / 探索成功率 / 操作成本比),和上一轮对比的升降。
- **问题清单**,每条问题统一格式:
  ```
  [类型] Bug(算错/崩溃) | 体验(能做但难) | 缺功能
  [影响场景] B03, B06, E05
  [证据] 截图 + 操作录屏 GIF + Agent 当时的想法 + 期望值与实际值
  [建议方案] 一句话
  [优先级] = 影响场景数 × 场景优先级 × 类型权重(Bug 3 / 缺功能 2 / 体验 1)
  ```
- 同类问题自动合并(比如"找不到日期部件"在 B03、B04、B06 都出现,合成一条)。
- 问题同步到 GitHub Issues(打 `agent-found` 标签),便于追踪。

## 7. 迭代节奏

```
每天(定时任务)                  每次改代码                         每周
─────────────────                ─────────────                     ──────
线上冒烟 5 个 P0 场景              脚本 Agent 全量回归(约 3 分钟)     探索 Agent 全量(55 场景 × 3 人设)
→ 失败就通知你                     → 不通过不合并                     → 出体验报告 → 选下周要做的 Top 5
```

**一轮迭代的动作**:探索报告选出 Top 5 问题 → Claude Code 在分支上实现 → 脚本回归 + 相关场景探索重跑 → 指标确实变好 → 你审核合并 → 打部署包上线。
**人工把关点**:合并代码、部署上线、调整场景优先级,这三件事始终由你决定。

## 8. 根据预判,前几轮大概率要做的改进

先列出来,用第一轮测试结果去验证和排序,不是直接开做:

1. **改成 Tableau 式"架子"布局**:顶部"列 / 行"两条横架 + "标记"卡片(颜色、大小、标签、详细信息、工具提示),字段直接拖进去,
   图表类型由架子上的字段自动推断(Show Me 逻辑),而不是先选 35 种类型再填通道。这是"好难用"最可能的根因。
2. **字段胶囊上的右键/下拉菜单**:聚合、日期粒度、**日期部件**(月份名、星期)、排序、快速表计算、筛选,都在胶囊上就地完成。
3. **计算字段**:简单表达式(`[利润]/[销售额]`)+ 常用快速表计算(合计百分比、累计、排名、同比/环比)。
4. **双击自动出图、撤销/重做、架子之间拖动胶囊**。
5. **交叉表 / 突出显示表**(Tableau 最常用的"图"其实是表)。
6. **仪表板**:多图拼板 + 一张图点击筛选其它图(Flint 有 board 和 linkCharts 能力可用)。

## 9. 分阶段落地

| 阶段 | 内容 | 产出 | 工作量 |
|---|---|---|---|
| 0 | 可测试性改造(§4.2)+ fixtures + 答案库 | 产品带 testid 和调试钩子 | 1 天 |
| 1 | 脚本 Agent + Oracle + 首批 20 个 P0/P1 场景 | 第一份覆盖矩阵,确认现状列 | 2 天 |
| 2 | 探索 Agent(3 种人设)+ 体验指标 + 报告页 | 第一份"好不好用"报告和 Top 问题 | 2 天 |
| 3 | 补齐 55 个场景;接 GitHub Issues;定时任务 | 每日冒烟 + 每周体验报告自动化 | 1–2 天 |
| 4 起 | 按报告迭代产品(§8),每轮回归 | 场景通过率、操作成本比逐轮上升 | 持续 |

**成功标准(建议)**:3 轮迭代后,P0 场景脚本通过率 100%,探索成功率 ≥ 80%,P0 场景操作成本比 ≤ 1.5。

## 10. 需要你确认的几件事

1. **探索 Agent 用哪个模型、走哪里跑**:在 Claude Code 里用 Playwright MCP 跑最省事;或者用 Claude API 写一个独立脚本,方便放进 GitHub Actions 定时跑。
2. **线上冒烟要不要做**:要的话,需要能从测试运行的地方访问 `152.136.222.86:39018`,并约定测试数据前缀和清理规则。
3. **第 8 节的"架子布局"改造方向**:你是否认可向 Tableau 的交互靠拢?如果认可,建议在第 1 阶段之后、第 2 阶段之前就先做,因为它会改掉大部分选择器和场景脚本。
